Présentation et stack

TOPilot est l’outil interne de gestion d’agence de Top 10 Stratégie (environ 11 utilisateurs). Il centralise clients, opportunités, missions, outils (toolbox), documents et wiki, pour limiter la dispersion des outils du quotidien.

Les opportunités et les missions sont le cœur du produit. L’interface est en français. Création et édition passent par des tiroirs latéraux droits.

Stack

  • Next.js 16 (App Router), React 19, TypeScript strict
  • Supabase : Auth, Postgres, RLS, Storage, Vault
  • Tailwind CSS 4, shadcn/ui, Phosphor Icons
  • DnD Kit (kanbans), Tiptap (wiki), Recharts (analyses)
  • Hébergement Vercel, gestionnaire de paquets npm uniquement

Sources de vérité dans le dépôt

  • Présentation produit courte : README.md
  • Journal des livraisons : suivi.md
  • Spec produit, UX, base et sécurité : dossier .cursor/rules/
  • Migrations SQL : dossier supabase/migrations/
  • Types générés Postgres : lib/supabase/database.types.ts

Les fichiers .cursor/rules/ restent la spécification détaillée. Ce document en extrait l’essentiel pour une reprise de projet.

Point critique : un seul projet Supabase sert à la fois au développement et à la production. Les tests manuels destructifs impactent les données réelles.

Démarrage local

Prérequis

  • Node.js 20 ou plus (la CI utilise Node 22)
  • npm (lockfile unique package-lock.json, jamais yarn ni pnpm)
  • Accès au projet Supabase TOPilot (URL et clés)
  • Accès au dépôt GitHub et aux variables Vercel si déploiement

Variables d’environnement

Copier .env.example vers .env.local puis renseigner :

  • NEXT_PUBLIC_SUPABASE_URL — public — URL du projet Supabase
  • NEXT_PUBLIC_SUPABASE_ANON_KEY — public — clé anon / publishable (RLS appliquée)
  • SUPABASE_SERVICE_ROLE_KEY — serveur uniquement — contourne la RLS (Vault, admin, Storage, must_change_password)
  • CRON_SECRET — serveur — Bearer attendu par les routes /api/cron/
  • NEXT_PUBLIC_SITE_URL — optionnel — origine pour les liens d’invitation Auth (en local : http://localhost:3000)

Ne jamais committer .env.local. Ne jamais utiliser la service role dans un composant client.

Installation et commandes

  • npm install
  • npm run dev — serveur de développement (souvent http://localhost:3000)
  • npm run build — build production
  • npm run start — serveur production après build
  • npm run lint — ESLint
  • npm run typecheck — vérification TypeScript
  • npm run knip — détection de code mort (exigé en CI sur main)

Avant de coder : lint + typecheck. Avant un merge vers main : lint + typecheck + knip + build.

Premier accès (bootstrap)

  1. Créer un utilisateur dans Supabase Auth (dashboard).
  2. Créer la première ligne collaborator via le Dashboard SQL / Table Editor (rôle postgres / service role), avec role = direction ou manager, status = actif, et un team_id valide.
  3. Une ligne setting est créée automatiquement (trigger), avec must_change_password = true par défaut.
  4. Se connecter : redirection forcée vers le changement de mot de passe, puis accès métier.

Les INSERT collaborator via l’application sont réservés Manager / Direction. Sans premier compte bootstrap, l’UI d’administration ne peut pas démarrer.

Migrations

Les migrations vivent dans supabase/migrations/, ordonnées chronologiquement.

  • Ne pas modifier une migration déjà appliquée en production : en ajouter une nouvelle.
  • Après changement de schéma, aligner lib/supabase/database.types.ts avec le projet Supabase.
  • Le détail du schéma cible est dans .cursor/rules/04_database_schema.mdc.md et 05_security_rls.mdc.md.

Architecture applicative

Vue d’ensemble

Le navigateur utilise des Client Components pour l’interactivité (kanban, drawers, formulaires). Les lectures simples passent sous RLS avec la clé anon. Les mutations sensibles, le Vault et le Storage passent par des Server Actions ou des Route Handlers.

Côté serveur :

  • createClient() — session utilisateur + RLS (lib/supabase/server.ts)
  • createAdminClient() — service role (lib/supabase/admin.ts)

Principes :

  • Server Components par défaut ; Client Components seulement si nécessaire
  • Mutations métier dans actions/*.ts
  • Service role uniquement côté serveur
  • Drawers sans URL : état local / contexte DrawerStackProvider, pas de routing dédié

Arborescence des dossiers

  • app/(app)/ — pages métier protégées (shell : sidebar, header, drawers, recherche)
  • app/auth/ — login, reset password, callback, update-password, access-denied
  • app/api/ — route handlers (proxy fichiers, crons)
  • actions/ — Server Actions par domaine
  • components/ — UI par domaine, components/ui (shadcn), components/drawers
  • lib/ — requêtes, types, helpers métier, clients Supabase
  • hooks/ — hooks React partagés
  • supabase/migrations/ — historique SQL
  • proxy.ts — gate session / collaborateur actif / mot de passe
  • .cursor/rules/ — spec produit et technique

Clients Supabase

  • lib/supabase/client.ts — navigateur (anon)
  • lib/supabase/server.ts — Server Components / Actions (cookies + anon)
  • lib/supabase/admin.ts — service role
  • lib/supabase/proxy.ts — refresh session et contrôle d’accès
  • lib/supabase/database.types.ts — types du schéma

Pattern de page liste

Exemple pour /clients, /missions, /opportunities, /documents, /tools :

  1. Server Component page.tsx : lit les searchParams (filtres, page, vue), appelle une query ou une RPC list_*_page.
  2. Client Component *-page-client.tsx : vues (Kanban / Cartes / Tableau), filtres, drawers, DnD.
  3. Server Actions : create / update / archive / delete + revalidatePath.
  4. Pagination côté serveur via RPC list_*_page (SECURITY INVOKER, respect RLS). Ne pas recharger tout le dataset pour paginer.

Kanban missions / opportunités : mode p_board (jeu filtré complet pour le board ; pagination uniquement en vues Cartes / Tableau).

Drawers empilés

DrawerStackProvider et DrawerStackHost permettent d’empiler des formulaires (exemple : mission → nouveau client → nouveau contact).

  1. L’état du drawer inférieur est conservé pendant l’empilement.
  2. Annuler le supérieur restaure l’inférieur tel quel.
  3. Valider le supérieur injecte la nouvelle entité dans le champ du formulaire parent.

Auth gate (proxy)

Fichier proxy.ts → lib/supabase/proxy.ts.

Pour chaque requête (hors assets) :

  1. Session Supabase valide ?
  2. RPC get_auth_gate_state : collaborateur lié, status, must_change_password
  3. Sinon redirection vers /auth/login, /auth/access-denied ou /auth/update-password

Les préfixes publics auth sont définis dans lib/auth/constants.ts.

Routes API

  • GET /api/documents/[id]/file — proxy du bucket privé documents (session + RLS, puis URL signée)
  • /api/cron/exchange-rates — sync des taux Frankfurter (1er du mois) ; header Authorization Bearer CRON_SECRET
  • /api/cron/mission-recurrence — génération des occurrences de séries de missions (quotidien)

Domaines lib / actions

Chaque domaine a en général queries.ts, types.ts, éventuellement list-filters.ts, et actions/domaine.ts pour les écritures.

Domaines principaux : clients, opportunities, missions, tools, documents, wiki, collaborators, categories, analyses, audit, search, settings, exchange-rate.

Modèle de données

Principes

  • Clés primaires uuid (gen_random_uuid)
  • Nommage snake_case ; les clés étrangères se terminent par _id
  • Horodatage timestamptz ; updated_at via trigger set_updated_at
  • Enums SQL en snake_case sans accents ; libellés français uniquement en UI
  • RLS activée sur toutes les tables
  • client, mission, opportunity : jamais de DELETE physique
  • collaborator : anonymisation (anonymize_collaborator) + status = sorti
  • audit_log : append-only, jamais de suppression

Carte des entités

  • team a plusieurs collaborator ; chaque collaborator a un setting
  • client a plusieurs contact_client
  • client porte opportunity ; opportunity peut porter mission
  • mission a un scope client (avec client_id) ou interne (client_id null)
  • tool a tool_access (référence Vault) et tool_subscription avec tool_subscription_price
  • exchange_rate stocke les taux mensuels
  • document (versionning via parent_document_id, vue document_latest)
  • wiki
  • category (utilitaire : outils, wikis)
  • category_business (métier : clients, missions, opportunités, pôles ; peut être privée)
  • document_type

Tables de jonction typiques : client_category, mission_tool, opportunity_document, wiki_category, team_category, etc.

Enums métier

  • collaborator.role : direction, manager, collaborator
  • collaborator.status : actif, inactif, sorti
  • mission.mission_scope : client, interne
  • mission.kanban_status : a_faire, en_cours, terminee, archivee
  • opportunity.kanban_status : suspect, prospect, besoin_specifie, proposition_envoyee, gagne, perdue
  • opportunity.priority : faible, normal, urgente, prioritaire
  • document.storage_type : supabase, url
  • tool_subscription.subscription_plan : mensuel, annuel
  • setting.theme : clair, sombre, systeme

Automatismes importants (triggers)

  • Opportunité — statut initial : nouveau client → suspect ; client déjà connu (mission ou opp) → besoin_specifie
  • Opportunité — probabilité : mapping statut → proba mini ; ne baisse jamais une proba déjà plus haute
  • Opportunité — archivage : gagne / perdue → is_active = false (symétrique au retour)
  • average_price : colonne générée price × probability_confirmation / 100
  • Mission — archived_at : posé à l’entrée en archivee, remis à null sinon
  • Mission — completed_at : posé à la première entrée en terminee ; conservé si archivée ensuite
  • Contact principal : un seul is_main par client ; promotion auto à la suppression
  • Prix abonnement : une seule ligne active (valid_to IS NULL) par abonnement et devise
  • Setting : créé automatiquement à l’INSERT collaborateur
  • Audit : triggers SECURITY DEFINER sur les tables métier + notes

Documents et Storage

Deux buckets :

  • documents (privé) — is_visual = false — lecture via /api/documents/[id]/file (URL signée)
  • visuels (lecture publique) — logos, avatars (is_visual = true) — URL publique directe

Chemin objet : {document_id}/{nom_fichier_assaini}.

Versionning : parent_document_id pointe vers la v1 ; la « latest » est calculée (COALESCE(parent_document_id, id) + max version_number). Pas de colonne is_latest.

RPC utiles : delete_document_version, delete_document_lineage (puis nettoyage Storage côté application).

Catégories et recherche

  • category : utilitaire (outils, wikis)
  • category_business : métier ; is_private = true masque l’entité (et cascade) aux Collaborateurs via RLS

Recherche FTS (tsvector) sur client, contact, collaborateur, team, opportunity, mission, tool, tool_access, document, wiki. audit_log exclu. Accès toolbox privés filtrés pour le rôle Collaborateur. Wiki indexé sur content_text, jamais sur le HTML.

Missions récurrentes

Logique mission_series + cron /api/cron/mission-recurrence pour matérialiser les occurrences.

Sécurité, authentification et RLS

Règles non négociables

  1. RLS sur toutes les tables, aucune exception.
  2. Seuls les collaborateurs status = actif accèdent à l’application.
  3. SUPABASE_SERVICE_ROLE_KEY jamais côté client.
  4. Mots de passe toolbox jamais en clair en base, ni exposés au client sans passage serveur.
  5. audit_log : écriture via triggers uniquement ; aucune suppression.
  6. must_change_password : jamais affiché dans l’UI ; mise à jour via server action + service role.

Rôles

  • Direction : accès complet ; offboarding collaborateurs ; suppression pôles ; accès toolbox privés ; /analyses ; /history
  • Manager : mêmes capacités sensibles que Direction pour le contenu privé, offboarding, analyses, historique
  • Collaborateur : CRUD métier standard ; pas d’accès toolbox privé ni catégories métier privées ; pas d’offboarding ; pas d’analyses ni d’historique admin

Il n’y a pas de rôle Admin séparé en V1.

Suppression physique

  • client, mission, opportunity : impossible pour tous les rôles
  • collaborator : impossible → anonymize_collaborator (Manager / Direction)
  • team et tool_access privé : Manager / Direction
  • autres tables métier courantes : tout collaborateur actif
  • audit_log : impossible

Helpers RLS

  • is_active_collaborator() — session liée à un collaborateur actif
  • current_collaborator_role() — rôle du collaborateur courant
  • can_access_* / has_private_business_category — masquage catégories privées et cascade

Piège connu : ne pas appeler can_access_mission(id) / can_access_opportunity(id) dans la policy SELECT de la même table (casse INSERT…RETURNING pour les Collaborateurs). Contrôler les colonnes de la ligne ; garder les helpers pour les jonctions.

Piège connu : les fonctions de triggers SECURITY DEFINER doivent rester GRANT EXECUTE TO authenticated (sinon permission denied for function audit_trigger_fn).

Vault (toolbox)

Flux de révélation d’un mot de passe :

  1. Le client appelle la server action (actions/vault.ts, ex. readVaultSecret).
  2. Vérification session + collaborateur actif.
  3. Lecture de la ligne tool_access avec le client session (RLS) — prouve le droit de voir l’accès, y compris is_private.
  4. Déchiffrement via service role / RPC Vault seulement après.
  5. Affichage ponctuel en Dialog ; pas de persistance localStorage ni URL.

Création : secret Vault avant INSERT tool_access. Suppression : secret Vault puis ligne (vérifier que vault_secret_id correspond). vault_secret_id est un nom texte, pas l’UUID interne Vault.

Storage

  • Upload et delete d’objets : service role uniquement
  • Bucket documents : lecture via route proxy après check session + RLS
  • Bucket visuels : lecture publique

Flux mots de passe

  • Première connexion (must_change_password) : bloqué jusqu’à /auth/update-password
  • Mot de passe oublié : Supabase Auth (resetPasswordForEmail) — ne révèle pas l’existence du compte
  • Changement volontaire sur /settings : ré-auth obligatoire (signInWithPassword avec le mot de passe actuel) puis updateUser ; session conservée ; ne touche pas must_change_password

Un compte inactif ou sorti peut techniquement reset son MDP Auth, mais reste bloqué par le gate (status ≠ actif).

Règles métier

Cœur produit

Les opportunités et les missions sont les axes centraux. Le pipe commercial va du suspect à la clôture (gagne / perdue). Une opportunité gagnée alimente la création de missions.

Client

  • Statut unique : is_active (manuel)
  • facilitator : booléen « Apporteur d’affaires »
  • Contact principal (contact_client.is_main) : toujours exactement un principal dès qu’il existe au moins un contact
  • Champs obligatoires à la création : client_name, website, main_collaborator_id

Opportunité

  • Toujours rattachée à un client_id ; contact optionnel
  • Au moins une date parmi due_date_at / end_at
  • Statuts Kanban (ordre UI = ordre enum) : Suspect → Prospect → Besoin spécifié → Proposition envoyée → Gagné → Perdue
  • Montant pondéré = average_price (calculé, non saisi)
  • entry_average_price figé à la création ; closed_at à la clôture
  • Création en deux temps dans le drawer (identification puis complément) pour permettre les liaisons documents / outils

Mission

  • mission_scope = client ⇒ client_id obligatoire ; interne ⇒ client_id null
  • Toggle UI « Interne » (distinct du toggle « Privé » des accès outils)
  • Statuts : À faire → En cours → Terminée → Archivée (Kanban « Archivée » = 3 derniers mois via archived_at)
  • Analyses : complétées = completed_at non null ; abandonnées = archivee et completed_at null
  • estimated_charge = « Temps vendu » (heures, manuel)
  • Liens outils = jonction mission_tool (sans credentials) ; les accès crédentialisés restent sur tool_access

Outils (toolbox)

  • Catalogue partagé tool
  • Accès tool_access : identifiant + secret Vault ; option is_private ; client_id optionnel (back-office client)
  • Abonnements : tool_subscription + historique de prix ; conversion EUR via exchange_rate (Frankfurter)
  • Suppression d’outil possible depuis la liste (contrairement client / mission / opportunité)

Documents, wiki et notes

  • Documents liés via jonctions ; liaison opportunité crée aussi client_document (le retrait depuis l’opportunité ne retire pas le lien client)
  • Versionning : nouvelle version = nouvel INSERT ; restauration = nouvelle version (copie), pas d’écrasement
  • Wiki : Tiptap ; content_html pour l’affichage, content_text pour le FTS ; éditable par tous les rôles actifs
  • Notes présentes sur client, mission, team, contact_client ; historisées (entity_type = note dans audit_log)

Vocabulaire UI

  • team → Pôle
  • opportunity.priority → Urgence
  • estimated_charge → Temps vendu
  • average_price → Montant pondéré
  • facilitator → Apporteur d’affaires
  • tool_access.is_private → Privé
  • mission_scope / toggle → Interne

CI/CD et opérations

Branches

  • main — production, protégée, pas de push direct
  • dev — intégration
  • type/description — feature / fix / perf… (ex. feature/pipe-commercial, fix/rls-tool-access)

Flux nominal : branche → PR vers dev → validation → merge → PR dev vers main → déploiement Vercel.

Le push GitHub est en général manuel sauf demande contraire.

CI GitHub Actions

  • Sur push / PR vers dev : lint + typecheck (ci-dev.yml)
  • Sur push / PR vers main : lint + typecheck + knip + build (ci-main.yml)

Sur main, les secrets Supabase CI sont des placeholders (le build ne parle pas à la vraie base).

Hébergement et crons

  • Vercel : déploiement auto depuis main
  • Variables d’env Vercel = mêmes clés que le projet Supabase unique
  • Crons déclarés dans vercel.json

Crons :

  • /api/cron/exchange-rates — schedule 0 6 1 (1er du mois) — taux de change Frankfurter
  • /api/cron/mission-recurrence — schedule 0 5 * (quotidien) — occurrences missions récurrentes

Auth des crons : header Authorization Bearer CRON_SECRET.

Runbook — situations courantes

Accès refusé après login Auth OK : vérifier collaborator (ligne liée à auth_user_id, status = actif). Sinon /auth/access-denied.

Boucle changement de mot de passe : setting.must_change_password encore à true. Mettre à false uniquement via le flux prévu (server action), pas depuis le client.

Impossible de créer un collaborateur depuis l’UI : normal si l’appelant n’est pas Manager / Direction, ou s’il n’existe encore aucun Manager / Direction (bootstrap Dashboard).

Mot de passe outil non révélable : session expirée, rôle Collaborateur sur accès is_private, ou secret Vault manquant / vault_secret_id incohérent.

Écritures métier en permission denied for function… : souvent un REVOKE EXECUTE trop agressif sur les triggers d’audit — rétablir GRANT EXECUTE TO authenticated (migration 20260807120000_restore_trigger_execute_grants.sql).

INSERT mission / opportunité échoue en 42501 pour Collaborateur : policy SELECT qui ré-interroge la table via can_access_*(id) pendant RETURNING — voir fix 20260807123000_fix_mission_opportunity_rls_returning.sql.

Build Vercel / ERR_REQUIRE_ESM (jsdom / DOMPurify) : conserver l’override jsdom@25.0.1 dans package.json. Ne pas le retirer lors d’un cleanup Knip.

Fichier Storage orphelin après delete document : la RPC a déjà supprimé la ligne DB ; un échec Storage est loggé pour nettoyage manuel — non bloquant pour l’utilisateur.

Monitoring

  • Logs applicatifs : Vercel Functions
  • Auth / DB : Dashboard Supabase
  • Journal produit des changements code : suivi.md

Conventions de contribution

Avant de modifier

  1. Lire ce document et la règle .cursor/rules/ associée au sujet.
  2. Travailler depuis dev ou une branche dédiée.
  3. Ne pas inventer de schéma, enum ou policy sans alignement avec les règles 04, 05 et 08.

Git

  • Branches : feature/…, fix/…, refactor/…, perf/…, docs/…
  • Commits : type: description en français (ex. feat: pagination serveur des missions)
  • Mettre à jour suivi.md pour toute action majeure
  • Pas de push force sur main ; pas de commit de secrets

Code

  • TypeScript strict ; noms de code en anglais ; UI et commentaires en français
  • Une responsabilité par fichier ; logique métier dans lib/ et actions/
  • Server Components par défaut
  • Enums SQL en snake_case sans accents ; mapping libellés dans l’UI
  • Pas de service role hors serveur
  • Réutiliser drawers et sections existants

Base de données

  • Nouvelle migration horodatée dans supabase/migrations/
  • Ne jamais éditer une migration déjà déployée
  • Mettre à jour database.types.ts après changement de schéma
  • Toute table : RLS + index sur FK + audit si l’entité est listée dans audit_log.entity_type

Checklist PR

  1. Comportement aligné règles métier / RLS
  2. npm run lint OK
  3. npm run typecheck OK
  4. Si cible main : npm run knip + npm run build OK
  5. suivi.md à jour
  6. Pas de clé / secret dans le diff
  7. Migrations documentées si schéma touché
  8. UI française cohérente (libellés, toasts d’erreur)

Où trouver l’historique des décisions

  1. suivi.md — chronologie des livraisons
  2. .cursor/rules/ — intention produit / technique
  3. supabase/migrations/ — évolution réelle du schéma
  4. PRs GitHub — discussions de revue

Contexte organisationnel

Utilisateurs cibles : collaborateurs internes uniquement. Pas d’environnement Supabase de staging séparé à ce jour : prudence maximale sur les scripts SQL et les tests manuels destructifs.
